## Context

当前游戏采用"相机跟随"设计：
- `GameField.tsx:87-88` 计算相机偏移：`ox = CX - p.x`, `oy = CY - p.y`
- `GameField.tsx:248` 玩家固定渲染在 `(CX, CY)`
- 其他实体通过 `e.x + ox` 产生反向位移

这种设计让玩家永远居中，但无法直观感受移动效果。

## Goals / Non-Goals

**Goals:**
- 玩家行星能在屏幕上自由移动
- 移动摇杆时能直观看到行星位置变化
- 保持游戏核心玩法不变

**Non-Goals:**
- 不改变实体生成/碰撞逻辑
- 不改变摇杆输入系统
- 不引入复杂的边界管理（如屏幕滚动）

## Decisions

### 1. 移除相机偏移系统

**决策**：移除 `ox/oy` 偏移量计算，所有实体直接使用世界坐标渲染。

**理由**：
- 简化渲染逻辑
- 玩家行星能直观移动
- 符合用户需求

**替代方案**：
- 保留相机但允许玩家离开中心 → 复杂度高，不必要
- 添加平滑相机跟随 → 用户明确要求自由移动

### 2. 玩家位置直接渲染

**决策**：将 `renderBody(CX, CY, p, true)` 改为 `renderBody(p.x, p.y, p, true)`

**理由**：
- 玩家行星直接在世界坐标渲染
- 移动时能看到位置变化

### 3. 边界处理策略

**决策**：不主动限制玩家移动范围，但保留离屏裁剪逻辑。

**理由**：
- 简化实现
- 玩家可以自由探索
- 离屏实体（包括玩家）会被自然裁剪

**风险**：玩家可能移出屏幕后找不到回来的路。

## Risks / Trade-offs

### 风险 1：玩家移出屏幕
**风险**：玩家可能移动到屏幕外，导致看不到自己。
**缓解**：保留离屏裁剪逻辑，玩家移出屏幕后会被裁剪，但可以通过摇杆反向移动回来。

### 风险 2：失去"世界在动"的视觉效果
**风险**：移除相机后，背景星空可能不再跟随移动。
**缓解**：检查 `StarField.tsx` 的实现，确保背景仍然能响应玩家移动。

### 风险 3：卫星轨道位置计算
**风险**：卫星轨道位置可能依赖相机偏移。
**缓解**：检查 `GameField.tsx:224-225`，卫星使用 `CX + Math.cos(a) * orbitRadius`，需要改为 `p.x + Math.cos(a) * orbitRadius`。

## Migration Plan

1. 修改 `GameField.tsx` 移除相机偏移计算
2. 修改玩家渲染位置为世界坐标
3. 修改卫星轨道位置计算
4. 测试边界情况
5. 验证背景星空是否需要调整
